# Промпт для мобильного приложения: вход в веб по QR

Реализуй в мобильном приложении Orbita пункт профиля «Вход по QR». Backend и веб уже реализуют контракт ниже. Мобильный проект меняй в его текущей архитектуре, переиспользуй существующую авторизацию, API-клиент, компоненты, локализацию и обработку ошибок.

## Сценарий

1. Пользователь входит в свой аккаунт в мобильном Orbita.
2. На странице входа веба выбирает «Войти по QR-коду».
3. В профиле мобильного приложения выбирает «Вход по QR»; открывается сканер камеры.
4. После сканирования приложение запрашивает данные устройства у backend и показывает отдельный экран «Разрешить вход в Orbita?».
5. Экран показывает текущий мобильный аккаунт, браузер/ОС (`deviceInfo`), IP (`ipAddress`) и срок действия (`expiresAt`). Кнопки: «Разрешить вход» и «Отмена».
6. Только явное нажатие «Разрешить вход» подтверждает вход. Само сканирование не авторизует веб.
7. После успеха показать «Вход разрешён» и вернуться в профиль. Сессию и токен мобильного приложения не менять. Веб самостоятельно получает свою отдельную сессию.

## Формат QR

QR содержит JSON, а не URL:

```ts
type OrbitaQrLogin = {
  type: 'orbita:qr-login';
  version: 1;
  id: string;        // ровно 32 символа [A-Za-z0-9_-]
  scanToken: string; // ровно 43 символа [A-Za-z0-9_-]
};
```

Проверяй объект, `type`, `version`, длину и формат полей до обращения к API. Отклоняй остальные QR с понятным сообщением. Не открывай адреса из QR, не меняй API host на основании сканируемых данных. Используй настроенный HTTPS API приложения. Не передавай мобильный JWT на веб и не сохраняй/не логируй `scanToken`.

## API для мобильного приложения

Все три запроса используют текущий JWT мобильного приложения:

```http
Authorization: Bearer <текущий JWT мобильного приложения>
Content-Type: application/json
```

Указанные ниже пути включают глобальный префикс `/api`. Если базовый URL API-клиента уже содержит `/api`, не дублируй его.

### 1. Отсканировать и получить данные для подтверждения

`POST /api/auth/qr/{id}/scan`

Тело: `{ "scanToken": scanned.scanToken }`.

Ответ:

```ts
{
  status: 'scanned';
  deviceInfo: string;
  ipAddress: string;
  createdAt: string; // ISO 8601
  expiresAt: string; // ISO 8601
}
```

Этот вызов закрепляет QR за текущим аккаунтом и текущей мобильной сессией. Повторное сканирование той же сессией допустимо до подтверждения. Другой аккаунт/сессия не может перехватить подтверждение. Данные браузера выводи обычным текстом, без HTML.

### 2. Разрешить вход

`POST /api/auth/qr/{id}/approve`

Тело: `{ "scanToken": scanned.scanToken }`.

Ответ: `{ "status": "approved" }`.

Вызывай только после успешного `/scan` и явного подтверждения пользователем. Мобильный JWT должен принадлежать той же сессии, которая выполнила `/scan`. Этот endpoint не возвращает JWT веба; веб завершает вход самостоятельно. Пока запрос выполняется, блокируй повторное нажатие. Успех означает, что вход разрешён; веб ещё может получить ошибку существующего лимита устройств.

### 3. Отменить вход

`POST /api/auth/qr/{id}/reject`

Тело: `{ "scanToken": scanned.scanToken }`.

Ответ: `{ "status": "rejected" }`.

Вызывай при «Отмена» или уходе с экрана подтверждения после успешного `/scan`, если вход ещё не подтверждён. При уходе best-effort отмена не должна блокировать навигацию. Не отправляй `/reject` после успешного `/approve`.

## Состояния и ошибки

- QR действует 120 секунд с момента создания в вебе, независимо от времени сканирования. Показывай оставшееся время; после истечения отключай подтверждение и предлагай обновить QR на компьютере.
- `400`: неверное тело запроса/формат. Покажи «Некорректный QR-код».
- `401`: мобильная сессия недействительна либо QR-токен неверен. Используй существующую обработку авторизации; после повторного входа нужно заново отсканировать новый QR.
- `409`: QR изменён, использован, отменён либо закреплён за другим устройством. Предложи обновить QR в вебе и сканировать заново.
- `410`: QR истёк или не существует. Предложи обновить его на компьютере.
- `429`: слишком много запросов. Покажи сообщение о повторе через минуту, не повторяй запросы в цикле.
- Сетевая ошибка: покажи возможность повторить действие до истечения `expiresAt`. Повтор `/approve` той же сессией допустим, пока веб ещё не забрал вход; если веб уже забрал его, будет `409`.
- Если аккаунт переключён или мобильная сессия завершена во время подтверждения, закрой экран, очисти сканированные данные и потребуй новое сканирование.
- Обработай отказ в доступе к камере, отсутствие камеры, повторные события сканера и уход приложения в фон. Сканер приостанавливается после первого распознавания, пока не завершится текущий сценарий.
- Не создавай собственную долгоживущую сессию: QR-вход использует существующий список устройств и лимит сессий. Отключение устройства доступно через существующий API сессий.

## Проверка

Проверь успешный вход после подтверждения, отсутствие входа после одного сканирования, отмену, истечение срока, неверный QR, повторное сканирование, другой аккаунт/устройство, отзыв мобильной сессии, сетевую ошибку и отказ в доступе к камере. Сохрани русскую и казахскую локализации.

## Справка о веб-контракте

Мобильному приложению эти endpoints вызывать не нужно:

- `POST /api/auth/qr` → `{ id, browserSecret, qrPayload, expiresAt, pollIntervalMs: 2000 }`.
- `POST /api/auth/qr/{id}/status`, тело `{ browserSecret }` → `{ status, expiresAt }`.
- `POST /api/auth/qr/{id}/exchange`, тело `{ browserSecret }` → `{ access_token, user }`, однократно после подтверждения.
- `POST /api/auth/qr/{id}/cancel`, тело `{ browserSecret }` → `{ status }`.

Возможные статусы веба: `pending`, `scanned`, `approved`, `rejected`, `cancelled`, `consumed`. `browserSecret` существует только в памяти веб-страницы и никогда не включается в QR. При неудачном обмене, включая лимит сессий, веб должен создать новый QR. Redis автоматически удаляет запрос по окончании срока; миграция PostgreSQL для этой функции не требуется.
